# コラム制作

KYUTEのコラムは、問い合わせの自然流入を増やすための記事です。**KYUTEにしか書けない一次情報が入っていない記事は作りません。** 検索上位の要約記事は、Googleの評価が下がる原因になります。

記事は `content/column/<slug>.md` に置き、プルリクエストの自動チェックが通ったあと、依頼者が「公開して」と頼むとマージして公開します。人の承認はありません。書き方の型は `content/column/_template.md`、品質基準は [references/review-checklist.md](references/review-checklist.md)、文章のルールは [references/writing-rules.md](references/writing-rules.md) です。

## モードの選び方

| 依頼 | モード |
|---|---|
| `/column auto ...`、または検索ワードと材料だけ渡されて「書いて」 | A：おまかせ |
| `/column plan ...`、または「一緒に考えたい」「構成から相談したい」 | B：じっくり |
| どちらとも取れない | 1行で確認する |

## 共通の準備（両モード）

1. `git status` で作業ツリーを確認する。`main` から `column/<slug>` ブランチを切る。他の人の未コミットの変更には触れない。
2. `npm run column:keywords` で既存の検索ワードを見る。**同じ・ほぼ同じ検索ワードの記事があれば、新規作成ではなく既存記事のリライトを提案する。**
3. 一次情報を集める。
   - 依頼文のメモ・ファイル・URL
   - 隣の private リポジトリ `../KYUTE/content-sources/column/`（あれば。メンバーが取材メモや社内データを置く場所）
   - `../KYUTE/context/`（会社の事実。価格・サービス内容はここと一致させる）
   - **一次情報が1つもないときは書き始めない。** 「この記事のために社内で確認したい質問」を3〜5個出して止まる。
4. 一次情報のうち、**公開してよいものだけ**を本文と `primarySources` に書く。顧客名・数字・社内事情は、掲載許可が確認できない限り伏せるか一般化する。kyute-hp は public リポジトリなので、ブランチに push した時点で中身が見える。

## A：おまかせ（`/column auto`）

入力の例：

```
/column auto
サービス: 採用動画制作
キーワード: 採用動画 費用
CTA: （省略可）
参考: https://...（省略可）
一次情報: 9月の撮影で〜だった／運動部のシゴト。の再生データ
```

1. **検索意図の調査**：WebSearch でキーワードを検索し、上位の記事を5〜10本読む。次をメモする。
   - 検索した人が知りたいこと（顕在・潜在）
   - 上位記事に共通する見出し（＝最低限必要な内容）
   - **上位記事に書かれていないこと**（＝KYUTEの一次情報で埋める場所）
2. **構成**：H2を4〜7個。一次情報を少なくとも1つのH2の中心に置く。共通見出しは短くまとめ、差分に分量を割く。
3. **執筆**：[文章のルール](references/writing-rules.md)に従う。数字には出典を付け、`references` に URL を入れる。本文中にサービスページへのリンクを1つ、関連コラムへのリンクを（あれば）2つ入れる。末尾のCTAは自動で入るので書かない。
4. **推敲**：`yomiyasu` スキルが使える環境なら、それで本文を整える。使えなければ文章のルールで自己チェックする。
5. **チェック**：`npm run column:check` のエラーを0にする。注意（△）は、直すか、理由をPRに書く。
6. **PR**：下の「プルリクエスト」に進む。

## B：じっくり（`/column plan`）

入力の例：

```
/column plan
テーマ: 採用動画が「見られない」本当の理由
読者: 採用動画をつくったが効果を感じていない人事
言いたいこと: 尺や画質ではなく、〜が原因だと思っている
材料: 〜社の事例、自分の撮影経験
```

各段階で**必ず止まって確認をもらう**。確認なしに次へ進まない。

1. **方針メモ**：読者、検索意図、この記事だけの主張（1文）、狙う検索ワード（候補を3つ、選んだ理由つき）、使う一次情報。→ 確認
2. **構成案**：H2・H3と、各見出しで使う一次情報・出典。→ 確認
3. **章ごとの執筆**：1〜2章ずつ書いて見せ、直す。依頼者の言葉・言い回しを優先する。
4. **全体の推敲**：通して読み直し、タイトル案を3つ（32文字前後、検索ワードを含む）と description 案を出す。→ 選んでもらう
5. **チェックとPR**：A の 5〜6 と同じ。

## プルリクエスト

1. ファイル名と `slug` を同じにする。`status: review`、`author` は依頼者（`content/authors/<id>.json` が無ければ作る。名前・役割・経歴を本人に確認する）、`mode` を記録する。`status: published` は依頼者が公開を頼んだときに入れる。
2. `npm run column:check` と `npm run build` を通す。
3. コミットして `column/<slug>` を push し、PR を作る。PR本文に入れるもの：
   - 狙う検索ワードと検索意図
   - 上位記事との差分（何をKYUTEの一次情報で書いたか）
   - 使った一次情報と、掲載許可の状態
   - `column:check` の注意（△）と、残した理由
   - 確認してほしい点
4. Vercel のプレビューURLで、下書きのまま記事を読める（プレビューは検索エンジンに載らない）。
5. 依頼者に、プレビューで読んで問題なければ「公開して」と頼むよう伝える。

## レビューコメントの反映

「PR #◯ のレビューコメントを反映して」と頼まれたら、`gh pr view <番号> --comments` と `gh api repos/{owner}/{repo}/pulls/<番号>/comments` でコメントを読み、該当ブランチに切り替えて直す。`column:check` を通してから push し、どのコメントにどう対応したかをPRにコメントで返す。

## 公開

「公開して」「PR #◯ を公開して」と頼まれたら、誰の依頼でも次の順で公開まで進める。人の承認は要らない。

1. 該当ブランチで、記事に `status: published` と `publishedAt`（指定が無ければ今日）を入れる。
2. `npm run column:check`（エラー0）と `npm run build` を通し、push する。
3. GitHub の自動チェック（`check`）が通るのを待ち、`gh pr merge <番号> --merge --delete-branch` でマージする。チェックが落ちたら直してからやり直す。
4. マージ後、Vercel の本番デプロイが終わったら `https://kyute.jp/column/<slug>` を開いて表示を確かめ、URLを依頼者に伝える。

`hidden: true` のサービスの記事は公開できない（チェックでエラーになる）。

## 非公開中のサービス

`lib/column/core.mjs` で `hidden: true` のサービス（現在はAIカジュアル面談・体験型会社説明会）は、下書きまでしか作れない。依頼されたら、公開はまだできないことを最初に伝える。

## やらないこと

- 一次情報なしで書く、上位記事を言い換えてつなぐ
- 掲載許可の確認できない顧客名・数字・ロゴ・動画を出す
- AIカジュアル面談・体験型会社説明会について、効果を言い切る（どちらも検証中のサービス。チェックでエラーになる）
- `main` に直接 push する（記事は必ずPRと自動チェックを通す）
- 依頼者が「公開して」と言う前に `published` にしてマージする

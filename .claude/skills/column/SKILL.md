# コラム制作

KYUTEのコラムの目的は、**検索から来た人事・経営者が、KYUTEへの資料請求・相談に進むこと**です。PVだけを増やす記事は作りません。

守ること（優先順）：

1. **KYUTEにしか書けない一次情報が無い記事は作らない。** 上位記事の要約は評価を下げます。
2. **本文だけでは完成ではない。** CV戦略（`strategy`）・アイキャッチ・必要な図表・本文中のCTA・プレビュー確認がそろって初めて完成です。`npm run column:check` が `status: review` 以降でこれを強制します。
3. **提供していないものを提供済みと書かない。** 資料・料金表・事例は、サイトにあるものだけをCTAにします（[CV設計](references/cv-design.md)）。
4. **公開は承認者が決める。** `reviewer` と `status: published` は承認者が入れます。

| ファイル | 中身 |
|---|---|

| [references/visual-design.md](references/visual-design.md) | ビジュアル構成、アイキャッチの作り方（AI生成・既存素材・コード描画）、図表のルール |

| `content/column/_template.md` | 記事の型（frontmatter と本文の書き方） |

## モードの選び方

| 依頼 | モード |
|---|---|
| `/column auto ...`、または検索ワードと材料だけ渡されて「書いて」 | A：おまかせ |
| `/column plan ...`、または「一緒に考えたい」「構成から相談したい」 | B：じっくり |
| どちらとも取れない | 1行で確認する |

## 共通の準備（両モード）

1. `git status` で作業ツリーを確認する。`main` から `column/<slug>` ブランチを切る。他の人の未コミットの変更には触れない。別のセッションが同じフォルダで作業していそうなら `git worktree add` で分ける。
2. `npm run column:keywords` で既存の検索ワードを見る。**同じ・ほぼ同じ検索ワードの記事があれば、新規作成ではなく既存記事のリライトを提案する。**
3. 一次情報を集める。
   - 依頼文のメモ・ファイル・URL
   - 隣の private リポジトリ `../KYUTE/content-sources/column/`（あれば。取材メモや社内データの置き場所）
   - `../KYUTE/context/`（会社の事実。価格・サービス内容はここと一致させる）
   - **一次情報が1つもないときは書き始めない。** 「この記事のために社内で確認したい質問」を3〜5個出して止まる。
4. 一次情報のうち、**公開してよいものだけ**を本文と `primarySources` に書く。顧客名・数字・社内事情・顧客の映像は、掲載許可が確認できない限り伏せるか一般化する。kyute-hp は public リポジトリなので、push した時点で中身が見える。
5. 画像の作り方を決める。依頼に「画像: 生成OK」「画像: 既存素材のみ」が無ければ、最初の返答で1回だけ聞く（AI生成は Figma AI のクレジットを使うため）。答えを待つ間も調査は進めてよい。詳細は [visual-design.md](references/visual-design.md#3-アイキャッチ)。

## A：おまかせ（`/column auto`）

入力の例：

```
/column auto
サービス: 採用動画制作
キーワード: 採用動画 費用
CTA: （省略可）
参考: https://...（省略可）
一次情報: 9月の撮影で〜だった／運動部のシゴト。の再生データ
画像: 生成OK（または「既存素材のみ」）
```

上から順に進め、各工程の成果物を残す。成果物はPR本文に載せる。

| # | 工程 | やること | 成果物 |
|---|---|---|---|
| 1 | 検索意図分析 | WebSearch でキーワードを検索し、上位5〜10本を読む。顕在・潜在の疑問、上位に共通する見出しを整理する | 検索意図メモ |
| 2 | 競合・差別化分析 | **上位記事に書かれていないこと**と、上位記事の図表の使い方を洗い出す。KYUTEの一次情報で埋める場所を決める | 差分リスト |
| 3 | CV戦略 | [cv-design.md](references/cv-design.md#1-cv戦略を決める) に沿って `strategy`（読者・意図・検討フェーズ・得られること・相談する理由）と主要CTAを決め、frontmatter に書く | `strategy`・`cta` |
| 4 | 記事構成 | H2を4〜7個。一次情報を少なくとも1つのH2の中心に置く。共通見出しは短く、差分に分量を割く | 見出し案 |
| 5 | ビジュアル構成 | [visual-design.md](references/visual-design.md#1-ビジュアル構成表) の「ビジュアル構成表」をつくる。アイキャッチのコンセプト、本文の図表・画像（目的・表現・作り方・配置・スマホでの見せ方）、CTAの位置 | ビジュアル構成表 |
| 6 | 本文執筆 | [文章のルール](references/writing-rules.md)に従う。数字には出典を付け、`references` に URL を入れる。関連コラムへのリンクを（あれば）2つ入れる | 本文 |
| 7 | 画像・図解の制作 | 構成表どおりに作る。アイキャッチは `npm run column:eyecatch` で 1600×900 のJPGにして `public/column/<slug>/` に置く。図解はSVG（コード描画）か表で作る。空のプレースホルダーで済ませない | 画像ファイル |
| 8 | 記事への組み込み | 画像を本文に入れ、alt とキャプションを書く。`eyecatch` を frontmatter に書く | 本文更新 |
| 9 | CTA最適化 | 本文中のCTA（`<!-- cta: id -->`）を、読者が行動したくなる直後に置く。末尾CTAが記事の主題に合うか確認する | CTA配置 |
| 10 | 推敲 | `yomiyasu` スキルが使える環境なら、それで本文を整える。使えなければ文章のルールで自己チェックする | 本文 |
| 11 | SEOチェック | `npm run column:check` のエラーを0にする。注意（△）は直すか理由をPRに書く。[品質基準](references/review-checklist.md)のA・C・Dを自己レビューする | チェック結果 |
| 12 | デザインチェック・ブラウザプレビュー | 下の「プレビューでの確認」を行い、スクリーンショットを撮る。品質基準のBを自己レビューし、気になる点は直す | スクリーンショット |
| 13 | PR | 下の「プルリクエスト」に進む | PR |

## B：じっくり（`/column plan`）

入力の例：

```
/column plan
テーマ: 採用動画が「見られない」本当の理由
読者: 採用動画をつくったが効果を感じていない人事
言いたいこと: 尺や画質ではなく、〜が原因だと思っている
材料: 〜社の事例、自分の撮影経験
```

各段階で**必ず止まって確認をもらう**。確認なしに次へ進まない。

1. **方針メモ**：読者、検索意図、検討フェーズ、この記事だけの主張（1文）、狙う検索ワード（候補を3つ、選んだ理由と商談につながる見込みつき）、使う一次情報、主要CTA。→ 確認
2. **構成案**：H2・H3と各見出しで使う一次情報・出典に加えて、**ビジュアル構成表**（アイキャッチのコンセプト、図表・画像、本文中CTAの位置）を見せる。アイキャッチは方向性の違う案を2〜3個、言葉かラフ画像で出す。→ 確認
3. **章ごとの執筆**：1〜2章ずつ書いて見せ、直す。依頼者の言葉・言い回しを優先する。図表はその章と一緒に見せる。
4. **ビジュアル制作**：アイキャッチと図解を仕上げ、サムネイル・スマホ表示の確認画像と一緒に見せる。→ 確認
5. **全体の推敲**：通して読み直し、タイトル案を3つ（32文字前後、検索ワードを含む）と description 案を出す。→ 選んでもらう
6. **プレビュー確認**：下の「プレビューでの確認」を行い、デスクトップ・スマホのスクリーンショットを見せる。**文章だけでなく、Webページとしての見え方をレビューしてもらう。** → 確認
7. **チェックとPR**：A の 11〜13 と同じ。

## プレビューでの確認

`.claude/launch.json` の dev サーバー（無ければ `npm run dev` で作る）を内蔵ブラウザで開き、`/column/<slug>` と `/column` を確認する。下書きはローカルとVercelプレビューでだけ表示される。

- デスクトップ（1280px前後）とスマホ（375px）の両方で、記事の最初の画面・図表・本文中CTA・末尾CTAのスクリーンショットを撮る
- アイキャッチ：一覧カードで記事が見分けられるか、詳細で上下が切れていないか
- 図表：スマホで文字が読めるか（目安は14px以上）、表は横スクロールで崩れないか
- CTA：押しやすいか（高さ48px以上）、リンク先が正しいか、前後の文章とつながっているか
- コンソールエラー、画像の読み込み失敗がないか

## プルリクエスト

1. ファイル名と `slug` を同じにする。`status: review`、`author` は依頼者（`content/authors/<id>.json` が無ければ作る。名前・役割・経歴を本人に確認する）、`mode` を記録する。`reviewer` と `status: published` は**承認者が入れる**。
2. `npm run column:check`・`npm run lint`・`npm run build` を通す。
3. コミットして `column/<slug>` を push し、PR を作る。PR本文に入れるもの：
   - 狙う検索ワード、検索意図、検討フェーズ、想定読者
   - 上位記事との差分（何をKYUTEの一次情報で書いたか）
   - CV設計：主要CTAと本文中CTAの位置・理由
   - ビジュアル構成表と、各画像の作り方（AI生成／既存素材／コード描画）。AI生成画像はそう明記する
   - 使った一次情報と、掲載許可の状態（顧客の名前・数字・画像・映像ごと）
   - デスクトップ・スマホのスクリーンショット
   - `column:check` の注意（△）と、残した理由
   - 確認してほしい点
4. Vercel のプレビューURLで、下書きのまま記事を読める（プレビューは検索エンジンに載らない）。
5. 承認者が `reviewer`・`status: published`・`publishedAt` を入れてマージすると公開される。

## レビューコメントの反映

「PR #◯ のレビューコメントを反映して」と頼まれたら、`gh pr view <番号> --comments` と `gh api repos/{owner}/{repo}/pulls/<番号>/comments` でコメントを読み、該当ブランチに切り替えて直す。画像やCTAの指摘なら、プレビューで再確認してスクリーンショットを付ける。`column:check` を通してから push し、どのコメントにどう対応したかをPRにコメントで返す。

## 公開設定（編集責任者だけ）

「PR #◯ を公開設定にして」と頼まれたら、依頼者が編集責任者（`docs/COLUMN.md` に記載）であることを確認してから、記事の `reviewer` に依頼者の id、`status: published`、`publishedAt`（指定が無ければ今日）を入れる。`column:check` を通して push し、「GitHubで Approve → Merge すると公開されます」と伝える。マージは人が行う。

## 公開後の改善

「◯◯の記事を改善して」「コラムの成果を見て」と頼まれたら、[cv-design.md](references/cv-design.md#4-効果測定) の指標（Search Console・Vercel Analytics の `column_cta_click`・問い合わせ記録）を依頼者に出してもらうか、見られるツールで確認する。検索CTRが低ければタイトル・description・アイキャッチ、CTAクリック率が低ければCTAの位置と文言、の順で直す。

## 非公開中のサービス

`lib/column/core.mjs` で `hidden: true` のサービス（現在はAIカジュアル面談・体験型会社説明会）は、下書きまでしか作れない。依頼されたら、公開はまだできないことを最初に伝える。これらのサービスのCTAを、他のサービスの記事に入れることもできない（チェックでエラーになる）。

## やらないこと

- 一次情報なしで書く、上位記事を言い換えてつなぐ
- 掲載許可の確認できない顧客名・数字・ロゴ・画像・動画を出す
- 「運動部のシゴト。」（自社メディア）の数字や動画を、顧客の支援実績のように書く
- AI生成画像を、実在の社員・顧客・撮影現場の写真のように見せる
- 提供していない資料・診断・料金シミュレーションを、あるかのようにCTAにする
- AIカジュアル面談・体験型会社説明会について、効果を言い切る（どちらも検証中のサービス。チェックでエラーになる）
- 画像・CTA・プレビュー確認が終わっていない記事を「完成」として報告する
- 承認なしに有料の画像生成サービスやAPIキーを追加する
- `main` に直接 push する、自分の記事を自分で `published` にする

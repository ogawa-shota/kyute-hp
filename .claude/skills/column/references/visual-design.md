# コラムのビジュアル設計

コラムは文章だけのページではありません。読者が**早く理解し、判断し、次の行動を決められる**ように、図表・画像・余白・強調を構成段階から設計します。ビジュアルは飾りではなく、それぞれに目的を持たせます。全記事に同じ図を入れることはしません。

## 0. 記事に適用するデザインの基本

コーポレートサイト（`docs/DESIGN.md` の Corporate site）の規則の上に作ります。独自の配色・書体は持ち込みません。

| 要素 | 規則 |
|---|---|
| 色 | 白・オフホワイト（`#f4f3ef`）の面、チャコール（`#1d1f24`）の文字と濃い面、アクセントは黄色（`#ffdb67`）だけ。淡い黄色（`#fff3cf`／`--brand-soft`）は補助の面。赤・青など別のアクセント色は使わない（グラフで系列を分けるときはチャコールの濃淡と黄色で） |
| 書体 | 本文は LINE Seed JP、数字・欧文ラベルは Inter。画像の中の文字もこの2つか、無ければ近いゴシック |
| 形 | 角丸（パネル16〜24px、ボタンは丸）。太すぎる枠線や影の多用はしない |
| 本文 | 17px以上（PCは18px）、行間2。見出しは H2 が下線、H3 が黄色の縦線（`app/column/column.css`） |
| 写真・映像 | 人と仕事が見えるものを優先。自社メディア「運動部のシゴト。」の映像は、必ず自社メディアと明記する |

デザインの方向性と、記事での具体的なやり方：

| 方向性 | 記事でやること |
|---|---|
| Photography-first | 説明の補助に、実際の撮影・制作の写真や動画を使う。ストック写真のような汎用画像は使わない |
| Human presence | 働く人・撮影する人が見える素材を選ぶ。AI生成で人物を描く場合は、実在の人物と誤認されない表現にする（後述） |
| Work visualization | 制作の流れ、費用の内訳、体制などの「見えない仕事」を図にする |
| Editorial design | 見出し・余白・図表のリズムで、スマホでも途中から読める構成にする。文字だけの区間が長く続かないようにする |
| Clear hierarchy | 1つの図で伝えることは1つ。一番大事な数字・項目だけ黄色やチャコールで強調する |
| Conversion-oriented | 判断材料（費用・比較・事例）の図表の直後に、本文中CTAを置けるように構成する |

## 1. ビジュアル構成表

構成案（見出し）を作ったら、すぐにこの表を作ります。`/column plan` では構成案と一緒に見せて確認をもらい、`/column auto` ではPR本文に載せます。

| 位置 | 目的（読者が何を理解・判断するか） | 表現 | 作り方 | スマホでの見せ方 |
|---|---|---|---|---|
| アイキャッチ | 記事のテーマを一目で伝え、一覧・SNSで見分けられる | 写真／AI生成画像／コード描画 | AI生成・既存素材・コード描画のどれか | 16:9。中央に主題を置き、左右が切れても伝わる |
| H2「費用は何で決まるか」 | 内訳と金額が変わる条件を比べる | 表 | Markdown の表 | 3列まで。超えるときは横スクロール |
| H2「制作の流れ」 | 期間と社内の作業量を見通す | フロー図 | SVG（コード描画） | 縦に並べる |
| H2「選び方」の直後 | KYUTEの料金を確かめる | 本文中CTA | `<!-- cta: price-recruit-video -->` | カード |

使わない理由がはっきりしている場所に、図を無理に入れる必要はありません。逆に、**数字の比較、手順、3つ以上の選択肢の比較、仕組みの説明**は、文章だけで済ませずに図表を検討します。

## 2. 表現の選び方

| 伝えたいこと | 表現 | 作り方と注意 |
|---|---|---|
| 料金・費用の比較、会社や方法の比較 | 表 | Markdown の表。列は3〜4まで、セルは短く。出典を表の直後に書く |
| 手順・制作の流れ・期間 | フロー図 | SVG。スマホ前提で縦に並べる。各ステップに期間や担当を添える |
| 数値の推移・割合 | グラフ | SVG。系列は2つまで。数字そのものをグラフ上に書き、凡例に頼らない。出典と集計日を必ず書く |
| 仕組み・関係・サービスの全体像 | 図解 | SVG。要素は5つ程度まで |
| 現場の様子・制作物 | 写真・動画 | 自社で撮影したもの、掲載許可のあるもの。YouTube はURLだけの段落でプレイヤーになる |
| 章の要点 | ポイントボックス | `> [!POINT]` で始まる引用。1記事に2〜3個まで |
| 補足・注意 | 補足ボックス | `> [!NOTE]` で始まる引用 |

Markdown の書き方：

```md
![制作の流れ。ヒアリング、企画、撮影、編集、納品の5段階を縦に並べた図](/column/<slug>/flow.svg "採用動画ができるまでの流れ（KYUTEの場合）")

> [!POINT]
> 見積もりの差は、撮影日数と出演者の人数で生まれます。

<!-- cta: price-recruit-video -->
```

- 画像に `"..."` でタイトルを付けると、図の下にキャプションが出ます。図表には原則キャプションを付けます。
- 画像は `public/column/<slug>/` に置きます。チェックで、ファイルの存在と alt を確認します。
- alt には、図が伝えている内容を書きます（「図」「画像」だけにしない）。表は本文として読めるので alt は不要です。

### SVG図解のルール

- `viewBox` の幅は 640 前後で作る。スマホ（約343px）で縮小されても読めるよう、文字は 26 以上（表示で約14px以上）、線は 2 以上。
- 縦長（例 640×800）を基本にし、横に3つ以上並べない。
- 色は「0. 記事に適用するデザインの基本」の色だけ。背景は白か `#f4f3ef`。
- 文字は `font-family="'LINE Seed JP','Hiragino Sans','Noto Sans JP',sans-serif"`。`<img>` で表示するとWebフォントは読み込まれないため、端末の日本語ゴシックで表示される前提で、文字を詰め込みすぎない。
- `<title>` を入れ、記事側の alt と同じ内容にする。
- 作ったら、内蔵ブラウザで記事を開いてスマホ幅でスクリーンショットを撮り、文字が読めるかを確かめる。

## 3. アイキャッチ

新しい記事には、**記事固有のアイキャッチが必須**です（`status: review` 以降はチェックでエラー）。

### 使われる場所

| 場所 | 表示 | 注意 |
|---|---|---|
| 記事一覧・関連記事のカード | 16:9、スマホで幅約343px | 小さくても主題が分かるか |
| 記事詳細の冒頭 | 16:9、角丸 | 上下左右が切れていないか |
| SNSシェア（OGP） | 1600×900 をそのまま使用（X は `summary_large_image`） | JPG推奨。一部のサービスは中央を正方形に切り抜く |
| 構造化データ（Article の image） | 同じ画像 | — |

### 品質基準

- 記事のテーマが直感的に伝わる。タイトルを読まなくても「何の記事か」の見当がつく
- 他の記事のアイキャッチと見分けがつく（構図・主題・色の配分を変える）
- KYUTEのトーン（白・チャコール・黄色、静かで上質）に合う
- 安っぽいAIイラスト、ありがちなストック写真風の画像、意味のないグラデーションに頼らない
- 主題は中央の 60% 程度に収める（正方形の切り抜き・スマホでも残る）
- **画像の中に文字を入れない**のが基本。入れる場合は短い言葉1つ（10文字以内）にし、サムネイルでも読める大きさにする。AI生成画像の中の日本語は崩れやすいので、文字は後からコードで重ねる
- 1600×900 のJPG、300KB以下（500KBを超えるとエラー）
- alt は、画像に写っているものを具体的に書く（タイトルの繰り返しにしない）

### 作り方の選び方

| 方法 | 向いている場面 | 手順 |
|---|---|---|
| 既存素材 | 掲載許可のある撮影写真がある。「運動部のシゴト。」の場面がテーマに合う | 素材を選び、`npm run column:eyecatch` で整える |
| AI生成 | 抽象的なテーマ、撮影素材が無いテーマ | 下の「AI画像生成」 |
| コード描画 | 費用・比較・流れなど、図形で表すと伝わるテーマ | SVG（1600×900）を書き、`npm run column:eyecatch` に渡す |

`public/works/` の動画サムネイルは 960×540 で、単独では解像度が足りません。使うときは複数枚を組み合わせたコード描画にするか、元の撮影素材を使います。

### AI画像生成

使える環境（2026-10 時点）：**Figma MCP の `generate_image`**。KYUTEの Figma（Proプラン）で Figma AI が有効です。新しい契約やAPIキーは不要ですが、**1回ごとに Figma AI のクレジットを消費します**。依頼で「画像: 生成OK」が出ていない場合は、生成の前に1回だけ確認します。

手順：

1. 構成表のコンセプトから、方向性の違うプロンプトを2〜3案作る（下の型を使う）。
2. `generate_image` を `width: 1920, height: 1080` で呼ぶ。`fileKey` に生成用の Figma ファイルを指定し、`download_assets` で取り出す（ファイルが無ければ `create_new_file` で「KYUTE コラム画像」を作り、`docs/COLUMN.md` に fileKey を記録する）。モデルは `gemini-3.1-flash-image` を基本にし、試作は `gemini-3.1-flash-lite-image` で回数を抑える。1記事あたりの生成は合計6回までを目安にする。
3. 生成した画像を見て、品質基準に合う1枚を選ぶ。合わなければプロンプトを直す。
4. `npm run column:eyecatch -- <slug> <画像> --preview-dir <scratchpad>` で 1600×900 のJPGにし、出力されたサムネイル（343px）と正方形の切り抜きを Read で見て確認する。
5. frontmatter の `eyecatch` に src と alt を書き、プレビューで一覧と詳細を確認する。
6. PR本文に「アイキャッチはAI生成（モデル名）」と書く。

プロンプトの型：

```
Editorial photograph style key visual for a Japanese B2B article about {テーマを英語で具体的に}.
Subject: {主題。例: a compact video camera on a tripod facing an empty meeting room table with interview notes}.
Composition: subject centered within the middle 60%, generous negative space on both sides, 16:9.
Palette: warm off-white (#f4f3ef), charcoal (#1d1f24), one warm yellow accent (#ffdb67).
Mood: calm, high-quality, documentary. Natural light.
Avoid: any text or letters, logos, watermarks, exaggerated 3D illustration, neon gradients, stock-photo smiles, recognizable real people.
```

人物を入れる場合は、後ろ姿・手元・ぼかしなど個人が特定されない表現にします。**AI生成画像を、実在の社員・顧客・KYUTEの撮影現場の写真として見せてはいけません。** 本文で「KYUTEの撮影現場」と書く箇所には、実際の写真だけを使います。

`generate_image` が使えない環境では、既存素材かコード描画で作ります。ほかの有料サービス（画像生成API等）を使いたい場合は、導入せずに、必要な構成と費用を依頼者に報告します。

### 最終確認

- `npm run column:check` でエラーが無い（ファイルの存在・置き場所・16:9・幅・容量）
- サムネイル（343px）で主題が分かる
- 正方形に切り抜いても主題が残る
- 記事詳細・一覧・関連記事で表示が崩れない
- 空の画像やダミーで完成扱いにしていない

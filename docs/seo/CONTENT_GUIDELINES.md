# SEOコラムの制作・更新基準

更新日：2026-10-16。既存 `.claude/skills/column/SKILL.md`、`docs/COLUMN.md`、同スキルの品質・CV・視覚表現ルールを実行手順とする。CodexとClaude Codeは同じMarkdownモデル・検査・公開境界を使う。

## 成果と記事の役割

最終成果は有効問い合わせ・商談・受注。表示回数、自然検索流入、記事CTAクリックは改善途中の指標。順位・記事本数・文字数・DRの上昇だけを成功条件にしない。

制作前に `strategy` を埋める。

| 項目 | 決めること |
|---|---|
| reader | 誰が、どの業務・判断で困っているか |
| intent | 検索した時に解決したい具体的な疑問 |
| stage | learn / compare / decide |
| value | 読後にできる判断・作業 |
| strength | KYUTEに相談する理由。既存の公開事実に限る |
| hypothesis（任意） | CTA配置などで、何がどう変わると考えるか |
| metric（任意） | 仮説を検証する先行指標と成果指標 |

既存記事の検索語と重なる場合、まずリライトで解決できるかを確認する。検索語だけで重複と断定せず、意図・対象読者・SERP・Search Consoleのquery→URLを比べる。

## 情報と信頼の扱い

- KYUTEの一次情報を中心に置く。取材・制作・運用の経験がない部分を経験談として作らない。
- 数字、他社の料金、制度、比較の条件には出典と確認時点を付ける。未確認値を推測で埋めない。
- 自社メディア「運動部のシゴト。」は自社メディアと明記し、顧客採用成果と混同しない。
- 顧客名・画像・映像・成果数値は公開許可を確認する。privateリポジトリの原文をそのままpublicリポジトリへコピーしない。
- `primarySources` は制作判断の根拠、`references` は公開できるhttp(s)の参考URL。前者は本文で自動表示しないが、frontmatter自体もpublicリポジトリの内容であることに注意する。
- `references` は記事末尾の「出典・参考資料」に表示する。事実を支える箇所にも直接リンクを置く。URL一覧だけで主張の裏付けが十分とはしない。
- `author` は既存のプロフィールID。組織著者は `type: Organization`、個人は `type: Person`。資格・担当経験・監修実績を創作しない。`reviewer` を設定した場合は既存プロフィールの名前・役割を内容確認者として表示する。
- AI生成画像を実在の社員・顧客・撮影現場と誤認させない。必要な生成表示とaltの確認は画像単位で行う。

## 見出し・本文・画像

titleとH1は主題と検索意図を明確にする。文字数は編集上の目安であり、Googleに固定の「32文字表示保証」があるわけではない。meta descriptionも固定文字数や順位上昇を保証しない。

導入は読者の判断課題と得られる内容を短く示す。H2/H3は判断の順に並べ、表・図・動画は理解のために使う。本文の文字数を満たすための水増しをしない。既存checkerの文字数・見出し数の警告は編集上の補助として読む。

記事固有の16:9アイキャッチ、内容に対応したalt、モバイルで読める表・図を用意する。本文画像の原寸・ファイルサイズを確認し、装飾画像に検索語を詰め込まない。

## CTAと検証

compare / decideの記事では、比較条件・費用・失敗回避などの判断材料を説明した直後に、既存CTASから選んだ本文CTAを置く。提供していない診断・資料・シミュレーターをCTAにしない。本文CTAは3個以内が目安であり、少ない場合にも自然な理由があればよい。

今回の比較記事は、費用説明の直後に公開料金へのカードを追加した。仮説は「比較中の読者が条件を確認しやすくなる」。料金CTAクリック率は先行指標であり、効果が出たとはまだ言えない。計測仕様は `MEASUREMENT_PLAN.md` を参照する。

## 公開・更新

1. 重複意図を確認し、一次情報と掲載許可をそろえる。
2. strategy、本文、出典、画像、CTAを整える。
3. `npm run column:check`、`node scripts/test-seo.mjs` とリポジトリ全体のlint/test/buildを通す。警告は理由を記録する。
4. desktop / mobileの実画面で、見出し・表・画像・出典の開閉・CTA・フォームへの到達を確認する。
5. 依頼者が公開を明示した記事のみ `published` にする。本番デプロイは今回の作業では未承認であり、勝手に行わない。
6. `publishedAt` はAsia/Tokyoの公開日。未来日なら本番ビルドから除外され、日付到来だけでは公開されない。公開日以降に再ビルドと承認済み本番デプロイが必要。
7. `updatedAt` は実質的な記事更新日だけを入れる。日付だけを新しくしない。公開日より前の更新日、存在しない日付は検査で拒否する。
8. 競合料金・リンク・自社の条件が変わった時、またはSearch Consoleと商談で意図のずれが見えた時に更新する。公開前後の評価期間・変更内容・観測値を記録する。

非公開サービスの公開禁止を維持する。FAQは読者の疑問に答える本文として整える。Google公式更新履歴ではFAQリッチリザルトは2026-05-07以降表示されないため、獲得施策としてFAQPageを追加しない。VideoObjectは動画の公開日・権利・メタデータ・ページ上での主役性を確認できる場合に別途検討し、未確認データを作らない。

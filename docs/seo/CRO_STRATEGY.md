# 問い合わせ・商談につなげる改善方針

確認日：2026-10-16（JST）。現行コードの観測、改善仮説、今回の実装を区別する。現状のCVRは未取得であり、改善率を約束しない。

## 1. 検索意図から行動を分ける

資料請求と無料相談は、検討者の準備度が違う。資料請求を増やしただけで成功とせず、営業が有効と判断した相談・商談への貢献を見る。

| 来訪者の状態 | ページで先に答えること | 主な導線 | 確認する成果 |
|---|---|---|---|
| 発注先を絞っている | 対応範囲・進め方・公開料金・相談で確認できること | 対象サービス→無料相談 | 有効相談、商談化 |
| 制作会社・費用を比較している | 比較軸、価格の条件、何が含まれるか | 料金→サービス資料 | 資料請求後の有効相談 |
| 導入を検討している | 活用場面、制作物の実例、自社との適合 | 制作事例→対象サービス | サービス送客、次段階への進行 |
| 採用課題を調べている | 原因の整理、動画が適する条件・適さない条件 | 関連記事・事例→サービス | 記事経由の後続行動 |

未提供の無料診断、料金シミュレーター、見積もりテンプレートを既存のオファーとして書かない。現行CTAカタログは`lib/column/core.mjs`、記事の戦略は`.claude/skills/column/references/cv-design.md`に従う。

## 2. すでに使える強み

- 2つのサービスページに、料金、FAQ、実際の映像、ページ内資料フォームがある。検索から来た人が別ページへ移らず資料請求まで進める。
- PCのヘッダー、フッター、モバイル下部に資料請求と無料相談がある。今回はこの見た目・優先順位を維持した。
- 資料フォームは会社名、氏名、メール、利用同意の3項目＋同意。送信中の無効化、エラー説明、結果へのフォーカス、リトライ用の安定したリクエストIDがある。
- コラムは記事ごとに読者・意図・検討段階・提供価値・相談理由を設定し、本文CTAを判断材料の後に置く仕組みがある。
- 「運動部のシゴト。」の動画を自社メディアと明示できる。顧客の導入成果として転用しない。

これはコード上の機能・内容の確認であり、利用者テストや高いCVRの証拠ではない。

## 3. 課題と施策の優先順位

| 優先 | 根拠・対象 | 施策と仮説 | 期待する貢献 | 工数・リスク / 検証 |
|---|---|---|---|---|
| P1 | コラム以外のCTAや新資料フォーム成功にイベントがない。HobbyではVercelカスタムイベントを集計できない | 安全な成功・CTAイベント＋任意GA4集計先 | どこで候補者を失うか判断できる | 実装済み、GA4有効化待ち。mockテスト、本番は承認後の受信確認 |
| P1 | `/contact`はGoogle Forms iframe。親ページは送信完了を観測できない | 回答シートをCRM正本へ転記し、計測の欠落を明示 | 相談数の過大評価を防ぐ | 運用は未開始。クリック数と相談完了数を分けて週次照合 |
| P1 | 顧客の支援実績は公開許可が未確認 | 公開許可がある実績だけ、課題→制作意図→公開範囲→確認できた成果を整備 | 比較段階の不安を減らす | 顧客許可が依存。現時点は自社メディアとして正確に表示 |
| P2 | `/download`は2サービスのフォームが並ぶ | サービスごとの資料の内容が閲覧前に分かるかを確認 | 選択後の離脱を減らす | まず資料内容を確認。文言テストは1サービスずつ |
| P2 | フォーム同意は表示されるが、会社名・氏名の必要性とプライバシー案内の充実度は要検討 | 営業運用上必要な項目だけを維持し、利用目的・保管/問い合わせ窓口を整える | 入力時の不安を減らす | 項目削除は通知/営業運用に影響するため今回は未変更。責任者確認後 |
| P2 | モバイルでは固定下部CTAと長いGoogle Formsが共存 | キーボード表示時、送信ボタン、エラー移動、戻る操作を実機で確認 | 完了前の操作障害を減らす | rootのブラウザーQAと分け、実機入力体験を確認。実送信不要 |
| P2 | 記事→サービス送客の設計はあるが流入/実行動データがない | 最初の比較・発注意図記事で価格/事例の直後に1つの文脈CTAを置く | 読者の疑問を解決した直後の行動を促す | `.claude/skills/column/`の品質検査。クリック/有効相談を28日単位で確認 |

公開料金や保証、初回トライアル条件、顧客実績をCV改善の名目で変更しない。サービスの見せ方は既存ブランドを維持し、GA4未接続の段階で大きなデザイン変更を同時に行わない。

## 4. 今回のローカル実装

1. 主要ナビ・CTAのクリックを識別する属性を追加し、`site_cta_click`を共通で計測する。本文や色、サイズ、CTAのリンク先は変えていない。
2. コラムは`column_cta_click`の名称・既存キー・位置区分を維持し、`href`をパスのみにする。共通CTAの二重カウントを防ぐ。
3. 新資料フォームはAPIが成功した時だけ資料請求イベントを送る。送信開始の同期ロックと同一試行の重複除外を追加する。解析サービスが失敗しても完了画面は表示される。
4. GA4測定IDが未設定ならGoogleタグを読み込まない。ID設定後も本番ホストだけで動作する。Hobbyで集計できないカスタムイベントの代替を準備する。

検証方法、実装範囲、送信しないデータ、GA4の有効化手順は[`MEASUREMENT_PLAN.md`](MEASUREMENT_PLAN.md)に集約する。

## 5. 最初に行う検証

### 仮説1：費用比較者には、料金を読んだ後の資料CTAが有効

- 対象：費用・制作会社比較意図のコラム。執筆時は一次情報と提供中の料金資料に基づく。
- 変更：比較表/費用条件の直後に、該当サービスの料金または資料CTAを1つ置く。記事末尾のサービスCTAを維持する。
- 主指標：同記事を含む自然検索セッションの`generate_lead`、CRMで確認できた有効相談。
- 診断指標：`column_cta_click`の`inline`と`end`、サービスの閲覧。
- 判断：同じ28日間、端末・流入構成を比較。件数不足時は検証期間を延ばし、率の差だけで勝ちとしない。

### 仮説2：相談前の期待が明確になると、相談の質が上がる

- 対象：`/contact`への導線。相談で得られる内容は実際に提供できるものだけを営業が確認する。
- 変更候補：「採用課題、制作の進め方、予算について相談できる」等の具体化。返信時間や無料範囲は未確認なら約束しない。
- 主指標：回答シート→CRMの有効相談率、商談化率。Google Formsの親ページクリックを完了扱いしない。
- 停止条件：営業対応が詰まり、初回返信の遅延が増える場合は送客量を増やす施策より対応フローを先に直す。

### 仮説3：フォーム成功率の低さが見えた場合は、入力体験の問題を先に直す

- 対象：新2サービスの資料フォーム。
- 最初の手順：APIエラー、入力形式、モバイルキーボード、フォーカス、送信完了までの待ち時間を確認する。
- 追加計測の条件：CTA→成功だけで原因を区別できない場合に限り、入力値を送らない`form_start`/分類済みエラーイベントを追加する。DOM自動取得や自由記述のエラー文字列は送らない。
- 主指標：受付成功とCRM登録の整合、フォーム障害の再現有無。入力項目を削る場合は営業に必要な情報を残せるかを合わせて検証する。

## 6. 改善会議の型

月1回、Web担当と営業担当が同じ問い合わせ月のデータを見て、次の順に確認する。

1. 計測が欠けていないか。GA4の設定やGoogle Formsの未計測を、CV悪化と取り違えない。
2. 有効相談は増えたか。増えていなければ、入口不足・送客不足・フォーム障害・対象外リードのどれかを分ける。
3. 有効相談から商談・受注につながっているか。進行中と失注を分け、成熟前のコホートで結論を出さない。
4. 次の変更を1つ決め、仮説・対象・変更日・指標・保留条件を記録する。順位やCTRだけが上がる施策を優先しない。

提案段階の施策は「効果がありそう」という仮説であり、実装済みの改善効果とは記載しない。

# 計測設計・運用手順

確認日：2026-10-16（JST）。この文書はローカル実装と有効化手順。未デプロイの変更を、本番で計測済みとは扱わない。

## 1. 判断の中心

最終指標は**自然検索をきっかけに発生した、有効な相談・商談・受注**。資料請求、ページ遷移、検索順位は、その原因を調べるための中間指標とする。

「有効な相談」の提案定義は、採用の当事者である企業から、現在提供している採用動画制作または採用YouTube運用について、具体的な課題・依頼が寄せられ、担当者が商談対象と判断したもの。営業売り込み、求職者、テスト、同一案件の重複を除く。資格判定は営業担当者が行い、クリックやフォーム成功から自動推定しない。

## 2. 監査で確認できた範囲

| 対象 | 変更前の確認結果 | 今回の状態・制約 |
|---|---|---|
| Vercel Web Analytics | `app/layout.tsx` に導入済み。プロジェクト設定の読み取りで `enabled:true` / `hasData:true` | データがあることと、期間別PV・流入数を取得したことは別。数値ベースラインは未取得 |
| Vercelカスタムイベント | コラムの `column_cta_click` のみコードに存在 | 本番プロジェクトのプランはHobby。Pro/Enterprise向けのカスタムイベント集計は現行プランで利用できない。アップグレードは行わない |
| GA4 / GTM | 設置コード・計測IDなし | 任意のGA4アダプターを追加。ID未設定ではGoogleのスクリプトもイベントも送信しない |
| Search Console | 既存コードに所有権確認タグなし | DNS確認などで別途登録済みの可能性があり、「未導入」とは断定しない。認証済みの検索データ未取得 |
| 新しい2サービスの資料フォーム | API応答を確認して完了表示。入力は会社名・氏名・メール・同意 | `response.ok && result.ok === true` を確認した時だけ完了イベントを追加 |
| 無料相談 | `/contact` 内にGoogle Formsの別オリジンiframe | サイト側から回答送信完了を直接検出できない。ページ閲覧・リンククリックを相談完了扱いしない |
| 既存LPの資料フォーム | `/lp`、`/lp/day-in-the-life`、`/lp/undo-job` / `/media` に別実装が残る | 既存の配信処理は今回未変更。新しい `material_request_success` の対象に含まれない |
| 商談・受注 | サイト内にCRM連携なし | 正本はアクセス制限された営業管理表/CRM。個人情報をAnalyticsへ送らない |

Vercelのカスタムイベントの利用プランは[公式ドキュメント](https://vercel.com/docs/analytics/custom-events)を確認した。プロジェクト設定の確認記録は `SEO_AUDIT.md` / `BASELINE_METRICS.md` を参照。

## 3. 実装したイベント

| 意味 | Vercelイベント名 | 任意GA4でのイベント名 | 発火条件 | 許可するプロパティ |
|---|---|---|---|---|
| ページ閲覧 | 既存pageview | `page_view` | 公開ページの初回表示・pathname変更 | 公開パスのみ。GA4の`page_location`は固定の本番origin＋公開パス |
| サイトCTA | `site_cta_click` | 同名 | コラム詳細以外で`a[data-cta]`をクリック | `path`, `cta`, `position`, `href`, `service` |
| コラムCTA | `column_cta_click` | 同名 | コラム詳細の本文・末尾・共通ヘッダー等のCTAクリック | 既存の`slug`, `service`, `cta`, `position`, `href`を維持 |
| 資料請求の受付成功 | `material_request_success` | `generate_lead` | `components/site/MaterialForm.tsx`でAPI成功確認後 | `path`, `service`, `form_id` |
| 有効相談・商談化・受注 | 未実装 | 自動送信しない | 営業担当者が確認 | CRM内で管理 |

GA4推奨イベントの`generate_lead`は初期のリード発生、`qualify_lead`は資格判定に使うという[公式定義](https://developers.google.com/analytics/devguides/collection/ga4/reference/events)に合わせた。今回は成功した資料請求だけを`generate_lead`とし、金額を根拠なく付けない。

プロパティ例：

```json
{"path":"/service/recruit-video","cta":"video-fv-download","position":"body","href":"/service/recruit-video","service":"recruit-video"}
{"slug":"cost-guide","service":"recruit-video","cta":"column-inline-price-recruit-video","position":"inline","href":"/service/recruit-video"}
{"path":"/download","service":"recruit-youtube","form_id":"culture-material"}
```

- `href`は遷移先のパスだけ。`#price`と`#download`の違いは既存の`cta`で区別する。移行前の`href`集計と直接比較せず、変更日を分析に注記する。
- `position`はサイトが`header / footer / mobile / body`、コラムが従来の`inline / end / site`。コラム上のヘッダークリックはコラムイベントだけで集計し、サイトイベントと二重に送らない。
- 対象の資料フォームは`/service/recruit-video`、`/service/recruit-youtube`、`/download`、および新広告LP `/lp/recruit-video`・`/lp/recruit-youtube`。フォームの`service`は表示文字列ではなく、許可した送信先から決める。
- ボタンクリック・入力検証失敗・HTTPエラー・通信失敗・`ok:true`のない応答では成功イベントを送らない。送信処理を同期ロックし、同じフォームインスタンス内の同一リクエストIDは一度だけ計上する。
- ページ再読込、別タブ、別端末をまたぐ人物の重複排除はしない。フォーム成功数は「受け付けた操作」の近似であり、ユニークリード数の正本はCRMとする。
- メール到着・PDF開封まで確認したイベントではない。APIが成功を返したことまでを測る。

実装：`lib/analytics.ts`、`components/analytics/`、`components/column/CtaTracker.tsx`、`components/site/MaterialForm.tsx`。非リンクの`data-cta`ラッパーはクリック対象にせず、Google Formsのiframe付近をクリックしても完了計上しない。

## 4. データ境界

カスタムプロパティに会社名、氏名、メール、入力値、自由記述、フォームのリクエストID、顧客ID、URLクエリ、ハッシュ、外部URLを含めない。公開経路を許可する関数を通し、API/承認URLや未知の経路は収集対象外とする。個人情報をURLパスやページタイトルへ載せないことも、今後の実装規約とする。

Vercelの`beforeSend`はイベントのURLからクエリ/ハッシュを除去する。これはSDKが渡すURLフィールドの対策であり、HTTPリクエストヘッダーのReferer、プロバイダー側の自動データ、外部iframeの収集まで保証するものではない。[Vercelの収集仕様](https://vercel.com/docs/analytics/privacy-policy)を踏まえ、有効化後に実際の通信を確認する。

GA4には公開パスから組み立てた`page_location`、パスを使った`page_title`、参照元のoriginのみを明示する。GA4の`page_location`は仕様上、protocolとhostを含む必要があるため、カスタム`path`/`href`とは形式が異なる。ブラウザーの現在URLをそのまま渡さない。

Googleシグナルと広告パーソナライズはコードで無効。これはユーザー同意管理の代わりではない。計測IDの設定前に、サイトの対象地域・利用目的に合うプライバシー表示と同意運用をサイト責任者が決める。必要な場合はCMP/同意取得後に起動する連携を追加してから有効化する。今回は同意UIを新設したり、広告連携を有効化したりしていない。

個人情報をAnalyticsに送らない運用は[Googleの公式ガイド](https://support.google.com/analytics/answer/6366371?hl=ja)に従う。UTM・検索語を含む任意クエリは今回収集しないため、キャンペーンの細かな分類はこの実装だけではできない。

## 5. GA4を無料のイベント集計先として有効化する手順

現在は無効。アカウント設定・本番反映は未実施。

1. 既存プロパティの有無を確認し、なければKYUTE所有のGoogleアカウント配下にGA4プロパティとWebストリームを作る。タイムゾーンを日本、通貨を円にそろえる。
2. **Webストリームの拡張計測をすべてOFF**にする。特にブラウザ履歴によるページ表示、フォーム操作、外部リンク、サイト内検索を自動収集しない。この実装がイベント所有者になる。
3. Googleシグナル、ユーザー提供データ、Google Adsとの自動連携を新たに有効化しない。保管期間・データ共有・プライバシー表示・同意運用を責任者が確認する。
4. 実際の測定IDだけを `NEXT_PUBLIC_GA_MEASUREMENT_ID` に設定する。例示IDで本番を有効化しない。ID自体は公開設定値だが、アカウント認証情報、APIシークレット、パスワードはチャット/GitHubに貼らない。
5. 環境変数の設定先はVercelの該当プロジェクトのProduction。設定変更・本番デプロイは依頼者の承認後。`NEXT_PUBLIC_*`はビルド時に取り込まれるため再ビルドが必要。ホストが`kyute.jp`または`www.kyute.jp`の場合だけ起動し、localhostとPreviewでは起動しない。
6. 本番反映後、通常のページ遷移とCTAクリックをDebugView/リアルタイムとNetworkで確認する。ブラウザ履歴の往復でpathnameごとに1回、クエリ/ハッシュだけの変更で追加pageviewがないことを確認する。フォーム実送信は別途承認された検証で行う。それまではmockテストで検証する。
7. `generate_lead`をキーイベントとして登録する。`site_cta_click`、`column_cta_click`、`page_view`をリードのキーイベントとして登録しない。必要なイベントスコープのカスタムディメンションは`service`、`cta`、`position`、`form_id`、`slug`、`path`、`href`。
8. 同じGA4計測IDをGTM、Vercel側挿入タグ、別Reactコンポーネントで重ねて設置しない。VercelとGA4の数字は別の収集基盤として比較し、足し合わせない。

`send_page_view:false`だけでは拡張計測の履歴イベントを停止できないため、手順2は必須。[Google公式・ページビューの測定](https://developers.google.com/analytics/devguides/collection/ga4/views?hl=ja)を参照。広告シグナルの設定は[公式設定リファレンス](https://developers.google.com/analytics/devguides/collection/ga4/reference/config)に基づく。

## 6. Search Consoleの確認・接続

1. KYUTEのアカウントで`kyute.jp`のドメインプロパティまたはURLプレフィックスプロパティが既にあるか確認する。既存なら閲覧権限だけで最初の分析は進められる。
2. 未登録ならドメインプロパティを作り、Google指定のDNS TXTで所有権確認する。DNSの変更は権限保有者が行う。HTMLタグの有無だけで所有権を判断しない。
3. `https://www.kyute.jp/sitemap.xml`を登録し、ホーム、2サービス、記事一覧のURL検査を行う。
4. 検索パフォーマンスを直近28日・その前の28日・直近3か月で出す。ページ、クエリ、デバイス、国の各表をエクスポートする。期間・検索タイプ・フィルタ・取得日を付記する。
5. 非指名/指名を定義する。指名の初期候補は`KYUTE / キュート / 運動部のシゴト`だが、汎用語「キュート」には別意図が混ざりうるためクエリを確認する。GSCでは匿名化等でクエリ行の合計と総数が一致しない場合があるので、残差を誤差扱いで消さない。

## 7. KPIの定義と判断

初期の数値目標・ベースラインは未取得。数字を埋めるための推測はしない。初月は計測の整合と流入構成を確かめ、翌月に予算・対応能力に基づく目標を決める。担当欄は推奨する役割であり、人のアサインは未確定。

| 指標 | 定義・分母 | 正本 / 主な切り口 | 担当・頻度 | 判断・注意 |
|---|---|---|---|---|
| 自然検索起点の有効相談 | 対象期間に初回相談、自然検索起点と確認でき、資格判定済みの案件数 | CRM / サービス・問い合わせ月 | 営業責任者・月次 | 主指標。流入不明は独立区分とし、自然検索へ補完しない |
| 商談化率 | 同じ問い合わせ月の有効相談のうち商談化した案件数 ÷ 同月の有効相談数 | CRM / 初回相談月コホート | 営業・月次 | 未追客/進行中を表示。異なる月の商談数を今月の問い合わせで割らない |
| 受注・粗利 | 同一相談コホートの受注案件数・確定粗利 | CRM / コホート・サービス | 営業責任者・月次/四半期 | 受注月の売上と、獲得月の施策評価を分ける |
| 自然検索の資料請求率 | organic searchの`generate_lead`数 ÷ organic searchセッション数 | 有効化後のGA4 / 着地ページ・サービス・端末 | Web担当・月次 | 人数のCVRではなく1セッションあたりイベント比率。複数請求なら100%超もありうる |
| 記事のCTAクリック率 | 当該記事の`column_cta_click`数 ÷ 当該記事の閲覧数 | GA4 / slug・cta・position | Web担当・月次 | イベント比率であり、クリックした人数の割合ではない。日付と対象ページを一致させる |
| サービスへの送客 | CTAイベントの`href`が対象サービスの件数 | GA4 / 元記事・cta・端末 | Web担当・月次 | リンククリックであり、遷移先読み込み成功と同一ではない |
| 検索クリック・表示・CTR | Google検索のクリック/表示、CTR＝クリック÷表示 | GSC / クエリ・ページ・端末 | Web担当・週次/28日比較 | 掲載順位は平均値。GA4セッションと同数である必要はない |
| フォーム成功とCRM登録の差 | API通知の受理件数とCRM登録件数を同期間で照合 | 社内通知/回答シート、CRM | 営業・週次 | まず欠落・重複・テストを確認。Analyticsはブロック等で欠測しうる |

## 8. 記事貢献とCRMをどうつなぐか

**今回、自動の人物単位結合は実装していない。** 記事slugをフォームAPIへ付けたり、氏名・メール・リクエストIDをAnalyticsへ送ったりしない。

- GA4では、organic searchセッションを対象に、`/column/…` → `/service/…` → `generate_lead`の経路データ探索を作る。記事が着地ページのケースと、途中で読んだケースを分ける。セッション内の観測経路は確認できるが、CRMのどの人か・別端末での行動・後日電話した人までは確定できない。
- CRMには管理者が生成した`lead_id`、受信日、問い合わせ経路（資料/Google Forms/メール等）、対象サービス、流入自己申告、流入根拠（自己申告/不明等）、参照記事（分かる場合のみ公開slug）、資格判定日と理由、商談日、受注日を記録する。個人情報はCRMのアクセス制限領域で持つ。
- Google Formsの回答シートと資料通知は、同じ企業・案件の重複を営業側で照合し、CRMの`lead_id`を付ける。公開GitHubに回答・通知・顧客一覧を保存しない。
- 最初は初回対応で「どこでKYUTEを知りましたか／参考になったページはありますか」を任意で聞き、回答をCRMだけに記録する。推定は事実の流入経路として上書きしない。
- 人物単位の自動結合が必要になったら、同意・保持期間・権限を決め、ランダムな非個人IDを使う設計を別途レビューする。ハッシュ化メールを一般のイベントパラメータに流す実装は採用しない。

Google Formsの完了は回答シートが正本。親ページの閲覧、iframeのロード、外部フォームへのクリック、離脱を完了とみなす代替実装は採用しない。

## 9. 運用と異常時の対応

| タイミング | 見るもの | 判断・アクション |
|---|---|---|
| 公開直後 | ページ表示・1クリック/1イベント・非PII・フォームmock | 計測不備があれば改善評価を始めず修正。受付機能への影響は最優先で戻す |
| 毎週 | 重要URL、GSCの除外、CRMへの転記漏れ | 前週に実受理があるのにAnalytics成功ゼロなら、タグ設定/プラン/計測漏れを先に確認 |
| 28日ごと | 同一期間・端末・チャネルの検索→記事→資料→有効相談 | 流入不足、記事送客不足、フォーム問題、リード品質を分け、次の1施策を決める |
| 90日ごと | 有効相談コホートの商談・受注、投下工数 | 問い合わせ後の成熟期間を確保してテーマへの投資を増減する |

サンプルが少ない時は率の上下だけで勝敗を決めない。テスト仮説と変更日を記録し、検索流入構成・季節・営業対応の変化を確認する。固定の「CVRが何%なら成功」という未根拠の閾値は置かない。
